## 0. 定论速览

**故障点（唯一）**：`Transient Analysis` 的 **`MAX_POINTS = 128000`**（Multisim 默认值）。
引擎被强制以 **1.00806 ns** 步长积分（= 1/31 MHz ÷ 32，与用户填的 TMAX 无关），
于是**累计瞬态点数达到 128 000 时**分析中止：

```
128 000 点 × 1.00806 ns = 129.03 µs      <-- 用户观测到的 "约 120 µs 失败"
```

对照全部观测：

| 观测 | 需要的点数 | 与 128 000 的关系 | 结果 |
|---|---|---|---|
| 测试 A：0→100 µs，TMAX 20 ns | **99 233** | 小于上限 | ✅ 成功（raw 已存档） |
| 测试 B：0→500 µs，TMAX 20 ns | 到达 128 000 时 | **在 129.0 µs 触顶** | ❌ 约 120 µs 失败 |
| 测试 C：100 µs，**Gear** | 步长更小 ⇒ 更快到顶 | 约 20–25 µs 触顶 | ❌ 更早失败 |
| 测试 D：5 ms | 远超上限 | 立即越界 | ❌ 无响应 → 堆损坏崩溃 `0xC0000374` |

**电路本身完全正常**（四重独立证明见第 3 节），**不需要任何电路改动**。

**修复（已应用）**：把该字段提到 **2 000 000**（200 µs 只需 198 400 点，留 10 倍余量），
并把 `TSTOP` 设为 200 µs、`method` 从 Gear 改回默认 Trapezoidal。`TSTART=0`、`TMAX=2 ns` 本已正确。

## 2. 故障原因（定论）

### 2.1 直接证据：解码 .ms14

Multisim 的 `.ms14` 是 **PKWare DCL Implode 压缩的 XML**，容器格式为：

```
magic  "MSMCompressedElectronicsWorkbenchXML" (36 B)
u64 LE 解压后总长度                           (= 1 412 621)
重复 {
  u32 LE 本段解压长度   u32 LE 本段压缩长度   <PKWare Implode 数据>
}                                              (每段 900 000 B)
```

用开源工具 [`cinderblock/electronics-workbench-decoder`](https://github.com/cinderblock/electronics-workbench-decoder)
（我自己写了 `D:\ewbwork\decode.mjs` 实现同一规格，`section 1: 900000 <- 94967`、`section 2: 512621 <- 88215` 全部校验通过）
解出 **1 412 621 字节、32 867 行**的 XML，其中瞬态分析块为：

```
ANALYSIS:list{TSTEP:string{calculate}
TSTOP:double{0.0001}          <-- 最后一次成功测试的 100 µs
TSTART:double{0}
TMAX:double{2e-09}
IC:string{auto_ic}
}
ANALYSIS_ID:long{3}           <-- 瞬态分析
PLOT_TITLE:string{...}
MAX_POINTS:long{128000}       <-- ★ 故障点：结果/绘图点数上限 = 128 000
DISCARD_PLOTS:long{1}
...
  25:list{IsEnabled:long{1}
  method:string{gear}         <-- ★ 用户测试 C 遗留的 Gear（其余 39 个分析都是 trapezoidal）
```

**全文件 40 处 `MAX_POINTS:long{128000}`，全部是 Multisim 默认值 128 000。**
（用户记忆中"曾设为 2 000 000"与实际不符 —— 实际一直是默认的 128 000，这也解释了为什么"提高过点数"却没生效：从未真正改到。）

### 2.2 为什么是 128 000 而不是别的

- 引擎把 TMAX 强制收紧为 `1.00806 ns`（引擎原文：`Info: tmax is automatically adjusted from 2e-09 to 1.00806e-09`，
  填 20 ns 时同样变成 `1.00806e-09`），所以点数 ≈ **992 000 点/每仿真秒**，与用户设置无关。
- `128 000 ÷ 992 000 点/秒 = 129.0 µs` —— 与"约 120 µs 失败"吻合（用户当时是目测进度）。
- Gear 步长更细 ⇒ 单位时间点数更多 ⇒ 在 20–25 µs 就触顶（观测一致）。
- 100 µs 只需 99 233 点 < 128 000 ⇒ 成功（与那条 3.97 MB 的 raw 完全一致）。

### 2.3 上限在"结果保留层"，不在求解器（关键区分）

同一套 `iplot` / `write-and-destroy-iplot` 机制（asys 生成的分析协议就是这一套，官方样例
`…\samples\LabVIEW Multisim API Toolkit\SPICE Command Line\CommandFile.cir` 里写得很清楚），
**由引擎直接执行时没有任何 128 000 上限**：

```
out_iplot200u.raw :  No. Points: 198468      <-- 0→200 µs，198 468 点，零错误
```

⇒ 引擎可以轻松产出并写出 198 468 点；**128 000 的限制是应用层（`asys.dll` 的结果/绘图保留缓冲）
施加的**，这正是 `asys.dll` 里 `MAX_POINTS` 与 `"Maximum number of points for plot should be larger than 10000"` 的含义，
也解释了为什么会报**通用的** `Internal simulation error.`（它紧挨 `Out of memory.`）
而不是引擎本来自带的专用报错（`Exceed max time points` / `Timestep too small` / `Does not converge` / `Singular matrix`）。

### 2.4 为什么可以排除电路（四重独立证明）

1. **同一原理图对照**：测试 A（100 µs）与 B（500 µs）用同一 `.ms14`、同一元件、同一参数，只差 TSTOP —— A 成 B 败。
2. **随点数而非时间**：Gear 在 100 µs 运行中 20–25 µs 就失败（点数增长更快）。
3. **引擎直驱 200 µs 零错误**（201 561 点；并复刻了 asys 完整分析协议，198 468 点，零错误）。
4. **COM API 直驱本电路的瞬态分析**：300 µs 与 **5 ms** 都无错误完成、内存恒定（122 MB / 143 MB）。
