## B. 重启后环境（23:30 之后）——关键发现

本机于 **2026-10-14 23:30:06 重启**（`LastBootUpTime`）。重启后的复现实验推翻了"A 段失败由电路工况决定"的解释：

| 尝试 | 网表与命令 | 结果 |
|---|---|---|
| C4_4Vpp_D50_5ms_tmax1ns | 已验收标称网表，仅 `tmax` 由 2 ns 改为 1 ns | 154.16 s 后 `Internal simulation error`（**基准自身也失败**） |
| C3_4Vpp_D10_5ms_tmax1ns | C3，tmax 1 ns | 状态残留在 STARTED（该轮被中断） |
| C3_4Vpp_D10_2ms / _1ms | C3，`tran 2n 2m 0` / `2n 1m 0` | 分别 26.91 s / 56.46 s 后失败（**耗时与 TSTOP 不单调**） |
| C3_4Vpp_D10_5ms_optrelax | C3，把容差写进网表 `.OPTIONS RELTOL=1e-3 TRTOL=7 ITL4=100` | 42.36 s 后失败（**放宽容差无效**） |
| C2_1Vpp_D50_5ms_rerun1 | **与 A 段成功那次逐字节相同的 C2 网表与命令** | 99.63 s 后 `Internal simulation error` |
| CHECK_REF_20us_rerun | 与 A 段成功那次相同的 20 μs 短窗 | **COMPLETED**，2,606,130 字节（与 A 段字节数完全一致） |

**结论（已证实）**：A 段的失败**不能**解释为"某些电路工况本身不可算"。同一 C2 网表在 A 段成功、在 B 段失败；同一 20 μs 短窗在两段都成功。故**单次失败不构成工况判定**。

**推断（中等置信度，未隔离验证）**：A、B 两段之间发生了重启，失败表现随之改变，故失败**很可能与本轮的环境状态有关**。但重启、驱动、系统更新等候选因素**均未被单独隔离验证**，不能断言环境就是根因。

**未证实（不主张）**：不能由上述证据推出"失败与工况无关"。本轮只测了 5 个工况、各工况重试样本极少，**不能排除工况相关的成功率差异**；要判定这一点需每工况固定次数的重复实验（本轮未做）。

## C. 重试即成功：全窗形式补充数据

B 段发现 `tran 2n 5m 4.5m 2n uic`（预充电 + TSTART 尾段）在该环境下无法通过重试恢复，而**全窗形式** `tran 2n 2m 0 2n uic`（同样预充电，但保存完整 0～2 ms）可以。以固定输入反复重试同一命令：

| 用例 | 尝试序列（同网表、同命令） | 成功者 |
|---|---|---|
| C2（基准校验） | BISECT_C2_2m | 第 1 次即成功，189.39 s、257,658,072 字节 |
| C1 | full2ms FAILED → full2ms_r2 | **r2 COMPLETED**，163.80 s、257,232,712 字节 |
| C3 | full2ms FAILED → _r2 FAILED → _r3 | **r3 COMPLETED**，132.34 s、258,149,732 字节 |
| C6 | full2ms EXCEPTION → _r2 | **r2 COMPLETED**，198.26 s、259,770,702 字节 |
| C7 | full2ms FAILED → _r2 … _r8 全部失败（含 2 次 EXCEPTION）→ _r9 | **r9 COMPLETED**，143.69 s、260,411,732 字节 |

**汇总：16 次尝试中 4 次成功**，且成功与否和先后次序无关（C7 连续 8 次失败后第 9 次成功）。这独立证实了失败的**概率性**：同一输入既可能成功也可能失败，失败模式在 `Internal simulation error`（引擎报错返回）与进程崩溃/提前退出之间随机分布。

**失败尝试一律保留、不覆盖、不计入成功数据。** 每个成功结论必须注明所采用的尝试标签。

## E3. runner 失效进程缺陷（2026-10-15 修复）

批次 2 首次运行时，C6_b1 失败后留下一个 Multisim 进程（PID 29292）：**0 线程、0 句柄、0 MB 工作集**，已完全退出，但进程记录因残留句柄未释放而留存。它无法被清理（`Stop-Process` 与 `.Kill()` 均返回拒绝访问），却占用了进程名。

旧 preflight 只按进程名计数，于是把它当成"已有引擎在跑"，**连续拒绝了 C6_b2 与 C7_b1**（`Preflight rejected: existing Multisim PIDs 29292`）。这两次尝试因此**根本没有启动仿真**，按纪律**不计入尝试预算**（已由 `run_budget.ps1` 的"无 status 文件即未启动"判定自动处理）。

修复内容：
- `run_one.ps1` 与 `run_budget.ps1` 均改为**以线程数/句柄数区分**真实引擎与失效记录：preflight 只拒绝真实引擎，失效记录仅登记（`preflight_defunct_pids`）。
- `run_one.ps1` 收尾增加**运行后清扫**（`leftover_killed` / `postrun_defunct_pids` / `postrun_live_pids`），避免引擎崩溃时漏掉的进程污染后续所有运行。
- 验证：在失效 PID 29292 在场时，`CHECK_C4_zombie_preflight` 正常启动真实引擎（PID 8516）并成功完成 20 µs 运行，字节数与已验收短窗一致。**故引擎本身仍可用，失效记录不构成阻塞。**

## F. 口径与纪律（补充）

1. **不得**把 `Internal simulation error` 或进程崩溃解释为某工况"电路不可行"的证据——同一 C2 网表有成有败，且基准网表自身也会失败。可确证的只是"单次失败不能判该工况不可计算"。
2. 长窗用例必须**设定重试预算**并逐一登记尝试；单次失败不构成工况判定。
3. **不得**宣称"失败与工况无关"或"环境是根因"——重启/驱动/系统更新未被单独隔离验证，且只测 5 个工况、各工况重试样本极少，**不能排除工况相关的成功率差异**。要判定需每工况固定次数的重复实验。
4. 全窗 2 ms 数据与已验收的预充电 5 ms 尾段**不是同一测量条件**（保存窗口与积分终点都不同；**初始条件相同，均为预充电**），分开记录，不得并入同一比较表。因 2 ms 组末五周期仍在建立过程，其**幅度/均值只能表述为"末五完整周期窗口测量值（2 ms 窗口，仍在建立过程）"**，不得称稳态值，也不宜简称为"瞬时值"（仍是对末五完整周期做 2 ns 均匀插值后的统计量）。
5. 稳定性结论继续引用 S03-04 第 6.3 节边界，不得因本轮补充数据而重新宣称"完全稳定"。
6. Multisim 仍必须串行；每次运行前 `run_one.ps1` 的 preflight 强制**无真实引擎**（`preflight_live_pids` 为空）。**失效进程记录**（0 线程 0 句柄，无法清理）不构成阻塞，但必须登记，不得混同为"有引擎在跑"。
7. 失败尝试的 `.log` / `_status.json` **原位保留**；成功用例必须注明采用的尝试标签。**尝试预算**：基准 ≤2 次、其余每组 ≤3 次；**没有 status 文件的调用视为未启动，不消耗预算**。
8. 测量**必须**使用冻结 6.2 口径。`analyze_fullwindow.py` 及 `fullwindow_summary.json` / `C*_full2ms_metrics.json` 为初版非合规输出，**已废弃，不得引用**。长窗补测数据的合规分析入口是 `analyze_longwindow_frozen.py`。
9. **单次（乃至固定预算内的有限次）基准成功只证明该次可运行**，不得据以宣布"环境已经恢复"；反之，本轮 11 次长窗全败也不得宣布"该条件不可计算"。
