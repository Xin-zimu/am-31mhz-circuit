# TSTART 短窗对照报告

日期：2026-10-14。目录：`simulation/v4_hardware/stage3_acceptance/副本专用文件夹/engine_acceptance_20261014/`。
运行目录：`D:\ms_xsp\stage3_acceptance\s0304_acceptance_20261014`。

**结论：TSTART 在本机被验证有效 —— 尾段运行与全窗运行在重叠窗内逐位相同（bit-identical），且不降低步长精度。可以在长冷启动运行中用它把保存量降低约 18 倍。**

## 1. 运行与结果

两个用例共用同一网表 `TSTART_*.cir`（sha256 `d6eff71d…`，与原 7 ms 源文件一致，**无 `.tran`/`.options` 行**），差别只在命令行的 `tran` 卡。

| 用例 | tran 卡 | 状态 | 用时 | 点数 | 起点 | 终点 | `.raw` |
|---|---|---|---:|---:|---|---|---:|
| `TSTART_full20us` | `tran 1n 20u 0 1n uic` | COMPLETED | 16.29 s | 20,412 | 0 µs | 20 µs | 2.60 MB |
| `TSTART_tail20us` | `tran 1n 20u 10u 1n uic` | COMPLETED | 8.25 s | 10,139 | **10.000998 µs** | 20 µs | 1.29 MB |

两者 `last_error` 均为空，都完整跑满 TSTOP=20 µs。

## 2. 逐位一致性验证（核心结论）

在全窗运行中截取 `t ≥ 10 µs` 的部分，与尾段运行整段对比：

| 变量 | 最大绝对差 | 最大相对差 | 是否逐位相同 |
|---|---:|---:|---|
| time | 0.000000e+00 | 0.000000e+00 | **True** |
| V(bb_in) | 0.000000e+00 | 0.000000e+00 | **True** |
| V(bbo) | 0.000000e+00 | 0.000000e+00 | **True** |
| V(v1) | 0.000000e+00 | 0.000000e+00 | **True** |
| V(v2) | 0.000000e+00 | 0.000000e+00 | **True** |

- 点数完全一致：**10,139 = 10,139**
- 时间轴逐位相同
- **重叠窗内最小步长也相同**：`4.386721e-11 s`（全窗）vs `4.386721e-11 s`（尾段）

最后一条尤其重要：它证明 **TSTART 没有改变自适应步进过程**。求解器仍然从 t=0 开始积分、用同样的自适应步长前进，只是**不保存** TSTART 之前的结果。这与 NI 文档的定义一致，但本次是**本机实测确认**，不是依据文档推断。

## 3. 一个需要记录的行为细节

请求 TSTART = 10.000000 µs，实际首点 = **10.000998 µs**，超出约 **998.3 ps**。

核对表明：尾段首点恰好等于**全窗运行中第一个 ≥ TSTART 的已接受步点**（`True`）。也就是说 TSTART 不产生插值点，报告从**跨越 TSTART 后的第一个自然步点**开始 —— 这是约一个步长上限（1 ns）量级的对齐误差，不是精度损失。

**使用时须注意**：若计划报告 8.5–9.0 ms，实际起点可能是 8.5009 ms 左右；末尾五个完整周期的判定应基于**实际返回的时间轴**，而不是请求值。

## 4. 保存量收益

| | 全窗 | 尾段 | 倍数 |
|---|---:|---:|---:|
| 20 µs 实测 | 2.60 MB | 1.29 MB | 2.02× |
| **9 ms 冷启动投影** | **≈1147 MB** | **≈64 MB** | **≈18×** |

投影依据：实测 127.47 字节/点；现有 7 ms 运行 925.5 MB / 7,127,505 点 = 129.84 字节/点，两者吻合。

**这直接解掉了原计划里"长窗保存量可能触发内存限制"的顾虑**（该顾虑有历史依据：5 ms GUI 运行曾在 3.469 ms 报内存不足，私有内存 828 MB）。9 ms 全窗保存约 1.1 GB，尾段只需 64 MB。

## 5. 对下一步的意义

原计划第 2 步"补长窗口末段证据，控制保存量"**已验证可行**，可以执行：

```
tran 1n 9m 8.5m 1n uic
```

- 计算量：9 ms 全窗积分（与 7 ms 同量级，7 ms 曾成功、10 ms 曾报 `Internal simulation error`，9 ms 位置未知，属于要验证的范围）
- 保存量：约 64 MB（安全）
- 输出窗口 0.5 ms = **15,500 个载波周期**，取末尾五个完整周期绰绰有余
- 判定方法沿用既有 `measure_stage3.py` 的 2 ns 均匀插值 + P98−P2 + 时间积分均值，与 7 ms 加权重算**同方法可比**

**风险**：9 ms 是否在求解器能力范围内尚未验证（10 ms 失败过）。若 9 ms 失败，退回到能跑通的最长窗口（7 ms 已知可行），并把"偏置在此窗口内仍未收敛"作为结论记录，而不是换判据。

## 6. 修复的 runner

原 `run_one.ps1` 把 `DoCommandLine` 当作同步调用，删掉了旧脚本的轮询循环，导致 0.08 s 就误判失败，随后复制日志时因文件被占用而抛错退出（exit 1）。

已修复并验证：

| 修复项 | 做法 |
|---|---|
| 完成判定 | 轮询等待非空 `.raw` 出现（它是命令脚本**最后一条** `write-and-destroy-iplot` 的产物，是可靠完成信号） |
| 状态记录 | `STARTED` / `COMPLETED` / `TIMEOUT` / `NO-RESULT` / `EXCEPTION`，含 `polls`、`wall_seconds`、`raw_bytes` |
| 日志复制 | 改为非致命；失败只记 `log_copy_error`，不影响结果判定 |
| 覆盖保护 | 已有非空 `.raw` 时拒绝运行 |
| 退出码 | 仅 `COMPLETED` 返回 0 |

两次运行均正常：16.29 s / 8.25 s，`last_error` 为空。
